## 🗺️ ドキュメントの読み方

### 初めてプロジェクトに参加する場合

```
1. README.md（概要を把握）
   ↓
2. DEVELOPMENT.md（環境構築）
   ↓
3. GAME_DESIGN.md（ゲームルールの理解）
   ↓
4. ARCHITECTURE.md（システム設計の理解）
```

### 新機能を実装する場合

```
1. GAME_DESIGN.md（仕様の確認）
   ↓
2. ARCHITECTURE.md（実装箇所の特定）
   ↓
3. DEVELOPMENT.md（実装手順の確認）
   ↓
4. コード実装
```

### バグを修正する場合

```
1. DEVELOPMENT.md（デバッグ方法）
   ↓
2. ARCHITECTURE.md（関連箇所の理解）
   ↓
3. コード調査・修正
   ↓
4. DEVELOPMENT.md（テスト方法）
```

### コードレビューを行う場合

```
1. ARCHITECTURE.md（設計原則の確認）
   ↓
2. DEVELOPMENT.md（コーディング規約の確認）
   ↓
3. コードレビュー
```

## 🔍 トピック別ガイド

### カード効果を追加したい
1. **GAME_DESIGN.md**: 効果の仕様を確認
2. **ARCHITECTURE.md**: 効果システムの設計を理解
3. **DEVELOPMENT.md**: 実装手順を確認

### APIエンドポイントを追加したい
1. **README.md**: API仕様の形式を確認
2. **ARCHITECTURE.md**: Adapter層の役割を理解
3. **DEVELOPMENT.md**: 実装手順を確認

### テストを書きたい
1. **DEVELOPMENT.md**: テストの書き方を確認
2. **ARCHITECTURE.md**: 各層のテスト方針を理解

### バランス調整を行いたい
1. **GAME_DESIGN.md**: カードバランスの指針を確認
2. **DEVELOPMENT.md**: カードデータの変更方法を確認

## 📝 ドキュメントの更新

### ドキュメントを更新すべきタイミング

- **新機能を追加したとき**
  - README.md: 新しいAPIエンドポイントなど
  - GAME_DESIGN.md: 新しいカードや効果
  - DEVELOPMENT.md: 新しい実装パターン

- **アーキテクチャを変更したとき**
  - ARCHITECTURE.md: 設計変更の反映

- **ルールを変更したとき**
  - GAME_DESIGN.md: ゲームルールの更新

- **開発プロセスを変更したとき**
  - DEVELOPMENT.md: 新しいツールや手順

### ドキュメント更新のベストプラクティス

1. **コードと同時に更新**: PR に含める
2. **具体例を追加**: コードスニペットや図を活用
3. **明確で簡潔に**: 技術用語は適切に説明
4. **最新の状態を保つ**: 古い情報は削除または更新
